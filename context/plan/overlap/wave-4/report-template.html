What your direction resolves

Keep as a product goal

  • Compose and edit with devices, plugins, MIDI, and samples.
  • Prepare instruments for live use; arrange, mix, and master through Bitwig.
  • Read and write detailed clip data. State coverage and losses.
  • Edit audio clips and device samples; obtain focused track audio for external analysis.
  • Support direct clients and retain an agent interface.
  • Keep primary host access useful when optional internals fail.

Reduce or move outside

  • Analysis, transcription, separation, and semantic library work move to external consumers.
  • Keep file authoring when it wins on capability or speed. Consider complete removal only when evidence makes it realistic.
  • Generative audio is outside Ghostnote's goal.
  • Operators generally record and export. Live launches, broad reuse, and platform expansion have lower priority. A lightweight early release is now a readiness goal.
  • Direct Ghostworks adapters and a separate client app still need a demonstrated workflow. HTTP for the bridge extension is accepted future intent.

Deprioritization does not remove accepted tools. Automated preset export is a dependency only when a selected workflow needs it.

Proposed scope rule: Ghostnote owns host facts and actions. External consumers own musical interpretation and library meaning. Minimal file and timing facts remain necessary for correct interchange.

TCP now; HTTP later

The user selected future HTTP transport for the bridge extension, for proxies, local-network use, and simple scripts. A small Python suite could be an independent API consumer. Intent recorded; no backlog item yet.

The document stays outside Java

Its current codec and bindings already live in TypeScript. Keep the format reusable. The extension still needs typed note data and guarded operations.

Primary-only mode must be proved

An unsupported internal feature should report its reason while primary work remains usable. Test initialization and client negotiation, not only a Grid refusal.

Three workflows, in the selected order

Selected order: 1. Song → 2. Performable sound → 3. Mix/capture. Use practical variations to exercise most of the matrix. These are templates; the user supplies current material at execution, when capability-specific acceptance is settled. Accepted choices.

1. Build a song from existing material

MIDI sketch→Detailed edits→Arrange + automate→Audio + track readback

High priority: detailed MIDI, arrangement, automation, audio clip CRUD, and sample state inside devices. Recheck pressure. Compare Producer Pal notation. Investigate quick inaudible post-device/pre-fader readback from an existing clip. Operator recording and final export are the default.

2. Make a sound performable

Useful controls→Live modulation→Grid instrument→Useful Grid depth

High priority: Grid construction and modulation as far as feasible. Revisit live setters through external references. Less common device state and nested devices are bonuses unless they are easy or required. Phase 11 retains Grid ownership.

3. Mix and capture a project

Balance→Useful routing + processing→Compare audio→Operator export

Use the required sends, Master, processing, and automation. Reuse focused readback or an operator export for external evaluation. General recording, automated stems, live performance control, and broad routing are not completion gates.

“Offline” means constructing a project without a live performance; Bitwig can still run. Current product footing and proof remain in wave 3. These cases do not establish new capabilities.

What does robust MIDI mean for this plan?

Select the fields and edits that matter: note start/duration, velocity, channel, same-pitch overlaps, per-note expression, clip loop/offset, meter, and tempo interpretation. The tested public-API reads cannot observe pressure, and current whole-clip rewrites can lose it. The external pressure handlers inspected use the same API; no workaround is demonstrated. R02 rechecks the experimental conditions and plans a minimal upstream reproduction if the defect persists. A faithful MIDI file representation does not imply that every field can be written live. Current limits and route inputs.

What would make graceful degradation real?

Primary reads and writes still work when optional internal resolution or initialization fails. The client accepts the supported primary contract. Unsupported steps refuse before mutation where possible. Partial and uncertain writes keep their effects and lock state. No automatic write retry or silent lossy substitution occurs. D15 and D49

D15 requires valid inputs and independent result evidence. It does not require deep undo or three full inventories. D49 requires honest revert reporting and adds no host calls. Both fit functional results with named preservation.

D54 supersedes D19’s blanket reversal obligation. Expected effects of the stated tool are acceptable; unintended changes are not. Normal undo, saves, and backups are general recovery. Existing tool behavior stays until a selected session changes it.
